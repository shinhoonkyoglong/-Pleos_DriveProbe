# DANGER 휴게시설 경유 E2E 수정

2026-11-13 · 브랜치 `codex/fix-rest-stop-e2e`

## 수정한 동작

### 주기적 재탐색 후 시설 확인 유지

확인의 원래 유효 기간은 24시간이다. 이전에는 약 5분마다 바뀌는 routeId까지 같아야 해서, 유효 기간 안에도 제안이 차단됐다.

이제 다음 조건을 모두 만족하면 기존 확인을 현재 경로 ID에 연결한다.

- 실제 안내 중이고 기존 경유지가 없으며, snapshot과 도착까지 완전한 TBT의 ID가 일치한다.
- 목적지의 실제 좌표/POI와 경로 옵션이 같다.
- 다음 세 휴게시설의 순서와 전체 방향 표기가 같다.
- 거리·ETA를 제외한 TBT 종류/코드/안내 문구의 순서가 같거나, 이미 지난 안내만 앞에서 빠졌다. 다른 도로·방향·시설·불완전한 목록은 거부한다.
- 최초 확인 시각부터 24시간 이내다. 재탐색으로 유효 기간을 연장하지 않는다.

제안 후 동의하는 동안 발생한 재탐색도 같은 경로 근거와 같은 시설로 재검사하고 최신 snapshot으로 요청한다. 조회 경계에서 ID가 바뀌면 읽기만 최대 세 번 재시도한다. 경유지 요청은 재시도하지 않으며 동의 토큰은 한 번만 사용한다.

저장 형식은 v2다. v1 기록은 원래 ID에서는 읽을 수 있지만 경로 근거가 없으므로 새 ID에서는 한 번 다시 확인해야 한다. 기존 Room 이력과 DB 스키마는 변경하지 않았다.

### 좌표와 POI가 생략된 경유 항목 판정

SDK가 모든 식별 정보를 생략하는 실제 반환을 처리하되 항목 생성과 시설 위치 검증을 구분한다.

| 상태 | 근거 | 표시 |
| --- | --- | --- |
| `VERIFIED_WAYPOINT` | 실제 좌표 또는 정확한 native POI로 시설 일치 확인 | 경유지 추가 확인 |
| `WAYPOINT_OBSERVED` | 원래 경유지 0개, 목적지/옵션/실제 안내 보존, 좌표와 POI 모두 누락, 방향을 포함한 전체 이름의 새 항목 1개를 같은 경로에서 두 번 안정적으로 조회 | 경유 항목 생성 확인 · 위치는 내비에서 확인 |
| `REQUEST_UNCONFIRMED` | 항목 누락, 상태 불일치, 다른 이름/방향, 충돌하는 좌표/POI 등 | 적용 여부 확인 필요 |

`(0,0)`을 위치로 비교하거나 공식 시설 ID를 native POI로 바꾸지 않는다. 새 이력 JSON v3에는 `waypointEntryObserved`와 `waypointIdentityVerified`, 표시 좌표/POI 원본을 따로 저장한다. 동의(`ACCEPTED`)와 내비 적용 상태도 계속 구분한다. 주행 요약의 휴식 권고/응답 횟수는 경유지 성공 횟수가 아니다.

### 시험 경유지 정리

이름만 같은 임의 경유지는 자동 삭제하지 않는다. 같은 프로세스가 보낸 요청과 안정된 재조회 결과를 담은 메모리 영수증이 있고, 2분 이내·동일한 현재 경로 ID/목적지/옵션/항목일 때만 진단 시험의 정리를 허용한다. 다른 경로, 프로세스 재시작, 만료, 다른 시설은 거부한다. 정상 음성 동의로 추가한 경유지를 생산 흐름에서 자동 삭제하는 동작은 없다.

## 검증

- 앱 단위 테스트 419개, 실패 0개. 동등 재탐색, 다른 도로/방향, 혼합 ID, 불완전 TBT, 원래 만료 유지, v1 호환, 동의 중 재탐색, 중복 요청, 생략/충돌 메타데이터, 정리 소유권, 결과 문구를 포함한다.
- Debug 앱·계측 APK 빌드와 `:app:lintDebug` 통과.
- 주행 도구 Python 테스트 10개와 PowerShell 판정 검사 28개 통과.

재현 코드는 `WaypointE2ETest`다. `waypointMode=voice`, `rerouteCount=2`, 고유 `probeRunId`, 실제 TBT에서 확인한 방향의 `directionBase64`를 명시한다. P·속도 0에서 확인을 저장한 후 실제 주기 재탐색 두 번 동안 재확인 없이 제안을 검사하고 같은 생산 DANGER 동작의 TTS → STT 동의 → 실제 추가 → 재조회 → 시험 항목 정리를 수행한다. 기본 계측 실행에서는 명시적 인수가 없으면 건너뛴다. 피로 단계는 수동 정차 시험 진입이며, 조건 엔진 전체 주행의 재시험이라고 표현하지 않는다. 음성 답변은 합성 한국어 WAV를 에뮬레이터 마이크 API에 공급한다.

### 실제 에뮬레이터 결과

Pleos Connect v2.1.0, Android 사용자 10, 실제 NaviHelper·TTS·AudioRecord·STT·Room을 사용했다. 시험 경로는 판교의 기본 에뮬레이터 위치 → 안성휴게소(부산방향), 다음 시설은 기흥휴게소(부산방향)다. 최종 빌드 APK로 재검증했다.

| 검사 | 결과 |
| --- | --- |
| 실제 5분 주기 재탐색 두 번 | 약 9분 동안 확인을 다시 저장하지 않고 두 번 모두 같은 시설 제안 성공. 각 routeId 변경과 `PLEOS_TBT_REVIEWED_PUBLIC_CATALOG` 출처 보존 |
| 실제 쓰기 시험 | 63.273초, 실제 경유 항목 1개 생성 → `WAYPOINT_OBSERVED` → 시험 항목 삭제/원래 안내 복원, 통과 |
| 실제 음성 동의 E2E | 87.243초, 실제 TTS 질문 → 합성 WAV의 실제 STT 인식 → `ACCEPTED`/`ACCEPT` → 실제 추가 → `WAYPOINT_OBSERVED` → 이력 저장 → 정리, 통과 |
| SDK 관측 | 경유 항목 기본 좌표 `(0,0)`, 표시 좌표 null, POI 정보 빈 값. `identityVerified=false`로 정직하게 기록 |
| Room 이력 90 | 실제 인식 응답과 동의, 요청 전송, 상태, 이력 JSON v3, 항목 생성 true/시설 식별 검증 false 일치. 수동 진단 이력으로 주행 집계에서 제외 |
| 최종 독립 재조회 | 안성휴게소 목적지·RECOMMENDED·ROUTE_GUIDING 유지, 경유지 0개 |
| 환경 정리 | 차량 P·속도 0·조향 0, 시험 heartbeat 종료, 음성/시험 foreground service 종료, 원래 호스트 마이크 enabled 복원 |

**재탐색 검증과 최종 음성 성공은 별도 실행이다.** 첫 통합 실행은 재탐색 두 번까지 통과한 뒤 합성 음성 주입 시점에 에뮬레이터 프로세스가 종료됐다. 재실행 시 에뮬레이터 자체 crash report의 `ERRLOG`는 `Failed to find ColorBuffer: 22`였다. 앱의 음성 성공으로 계산하지 않았다. 소프트웨어 렌더러로 콜드 부팅하고 내비 초기화 후 쓰기·음성 시험을 각각 다시 실행해 통과했다. AVD 데이터는 초기화하지 않았다. 소프트웨어 렌더러는 이번 실행 인수이며 프로젝트 설정 변경이 아니다.

원본 증거는 Git에서 제외한 `artifacts/driving-tests/rest-stop-fix/`에 보존했다.

- `periodic-before-crash.json`: 실제 경로 ID 변경 두 번과 재확인 없이 제안 유지
- `fix-write.json`, `fix-write.log`, `fix-write.txt`: 실제 추가/정리 통과
- `fix-voice.json`, `fix-voice.log`, `fix-voice.txt`: 실제 음성 동의·추가·이력·정리 통과
- `database-check.json`: Room 원본 대조 11개 검사 통과
- `final-inspect.json`, `final-vehicle-state.json`, `final-services.txt`: 최종 안내/정차/서비스 확인
- `verification-summary.json`: 검증 결과 요약

SDK가 생략하는 시설 좌표/식별자 자체를 복원한 것은 아니다. 촬영에서는 ‘경유 항목 생성 확인’과 ‘위치까지 검증’을 구분해 설명해야 한다. 2026-11-13의 앞선 실제 조건 엔진 주행 결과는 [주행 E2E 기록](driving-test-e2e.md)에 별도로 남아 있다.
