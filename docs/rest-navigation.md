# 경로상 다음 휴게소 제안 — 2026-11-12

## 최신 결정과 실제 상태

- 졸음쉼터 공공데이터 사용은 보류했다. CSV 카탈로그 로더·변환 스크립트를 제거했다.
- 목표는 **현재 안내 경로의 진행 방향으로 다음에 만나는 휴게소를 이름·예상 도착 시간과 함께 제안 → 명확한 동의 → 그 휴게소만 경유지 추가**다.
- 주변 직선거리 후보를 추린 뒤 최단 ETA로 고르던 이전 구현을 제거했다. 그것으로 경로상 다음 휴게소를 보장할 수 없다.
- 사용자가 보여준 내비 화면에는 용인휴게소·덕평휴게소 등 경로 안내 항목이 있었다. 이를 계기로 SDK의 TBT 목록을 다시 확인했다.

**확인된 SDK 단서:** `getTBTInfo()` → `onTBTInfo(List<TBTInfo>)`. `TurnType`에는 `TURN_ENTER_SERVICEAREA(41)`와 `TURN_RESTAREA(99)`가 있다. `TBTInfo` 필드는 type / distance / description이며, 좌표·POI ID·소요 시간은 없다.

따라서 “휴게소 유형을 포함한 내비 안내 목록을 읽는 API가 있다”는 것은 확인했다. SDK에 경로상 휴게소 단서 자체가 없다고 한 이전 판단은 이 확인으로 수정한다.

### 사용자 실행으로 확인한 실측

사용자가 `Test-RestNavigation.ps1`을 실행해 정식 Gradle 빌드·앱/시험 APK 갱신 설치·지정 계측 시험 1건 성공을 확인했다. 반환값은 TBT 51개이며 마지막 항목은 도착 안내였다. 이 경로에서는 도착까지 이어지는 목록이 왔지만, 모든 경로·모든 버전에서 목록이 완전하다고 일반화하지 않는다.

| 관측 | 해석과 반영 |
| --- | --- |
| code 41 10개 중 첫 항목이 하이패스센터 | 41을 곧바로 휴게소로 분류하면 안 된다. 명시적인 하이패스센터는 제외 |
| 용인졸음쉼터 code 99, 이후 용인휴게소 code 41 | 졸음쉼터 제외 후 첫 실제 휴게소 후보는 용인휴게소 |
| 용인휴게소 8,200m, 이후 덕평휴게소 1,700m | distance는 현 위치부터의 누적 거리가 아니다. 숫자 최솟값으로 덕평을 선택하면 잘못된 순서 |
| 이후 여주·충주·괴산·문경·선산·칠곡·청도새마을휴게소 | 수신 순서에 따른 휴게소 후보를 추출할 수 있음 |

41과 시설명 형식을 함께 확인한다. `휴게소` 이름이 확인되는 후보만 허용하고, 앞에 분류 불가능한 41 시설이 있으면 뒤의 시설을 다음 휴게소라고 단정하지 않는다. 방향이 이름에 포함되면 그대로 보존한다. 이름만으로 정확한 시설 좌표·방향까지 해결됐다는 뜻은 아니다.

구간 거리로 보이는 반환값을 모두 합산한 수치를 실제 경로 거리나 ETA로 사용하지 않는다. 정확한 거리 의미와 주행 중 목록 갱신은 추가 검증 항목이다. 이번 실제 원본 로그는 사용자 대화에 있으며, 전체 이동 경로와 routeId를 저장소에 복사하지 않았다.

### 실제 경유지 추가 화면 확인

사용자가 같은 앱 화면에서 실제 추가·복원 시험을 실행한 뒤 제공한 내비 화면에서 다음을 확인했다.

- 기존 최종 목적지가 유지된 상태에서 `경유지 1개 포함`이 표시됨.
- 실제 안내 목록에 `용인휴게소 강릉방면`이 별도 경유지로 표시됨.

등록한 실제 시설의 경유지 추가와 최종 목적지 보존은 내비 화면으로 확인했다. 이후 좌표 누락 대응 버전의 사용자 결과 화면에서 시험 경유지 삭제·원래 안내 상태 복원(`삭제·복원=VERIFIED`)도 확인했다. 정확히 동일한 원래 경로 형상 복원이나 실제 음성 동의부터의 통합 검증은 별도다.

화면 이탈 대응 이후 사용자가 제공한 결과 화면에서 최근 결과 보존은 확인했다. 해당 실행은 `추가=REQUEST_UNCONFIRMED`, `삭제·복원=FAILED`이며 삭제 전 컨텍스트 검사에서 차단되었다. 어느 비교 항목이 다른지는 기존 메시지로 확정할 수 없다. 후속 진단으로 `ADD_UNCONFIRMED`와 `CLEANUP_CONTEXT_MISMATCH`에 목적지·옵션·안내 모드·경유지 개수·좌표 일치 여부, 요청 좌표와 반환 경유지의 거리 차이를 표시한다. 완료 이벤트 수신 여부도 추가 확인 실패 로그에 남긴다. 검사 조건이나 좌표 허용 거리를 완화하지 않는다. 실패 상태의 시험 경유지는 내비에서 확인·정리한 뒤 다음 시험을 진행한다.

## 1. 지금 바로 시험할 기능

Debug 앱의 **내비 조회 → 내비 안내 목록 읽기**를 사용한다.

- 기존 NaviHelper 인스턴스·리스너와 requestMutex를 공유한다.
- 실제 내비의 TBT를 조회한다. 모의 목록으로 대체하지 않는다.
- TBT 조회 전후 목적지·경로 id·경로 옵션·안내 모드를 비교한다. 중간에 경로가 바뀌면 결과를 거부한다. 읽기 전용 원본 조회는 미검증된 빈 경유지 콜백에 의존하지 않는다. 실제 경유지 쓰기 전에는 경유지도 별도 확인한다.
- 수신된 순서대로 원본 유형·유형 코드·설명·거리(m)를 표시한다.
- 코드 41과 시설명을 함께 확인해 휴게소 후보를 식별한다. 하이패스센터와 99 졸음쉼터는 이번 제안 대상에서 제외한다.
- 화면 조회는 P·속도 0·실제 CarService UX 제한 없음 조건이다. 경로 변경과 음성 녹음을 하지 않는다.

**거리 숫자를 정렬해 가장 작은 것을 고르지 않는다.** 사용자가 보여준 화면처럼 여러 안내 항목의 거리 표시는 구간 거리일 수 있다. SDK 반환 순서·거리 의미·이미 지난 항목 포함 여부를 실제 화면과 대조해야 한다.

### 실행 명령

Android Studio의 호환 Gradle JDK(17/21) 환경에서 프로젝트 루트:

```powershell
.\scripts\Test-RestNavigation.ps1
```

이 스크립트는 단위 테스트·앱/시험 APK 빌드 후 `install -r`로 갱신 설치하고 **지정된 NaviWaypointProbeTest만** 실행한다. 기본 실행은 조회 전용이다. 기존 목적지·DB를 지우거나 경로를 취소하지 않는다. 에뮬레이터 Android 사용자는 10이다.

시험 전 내비에서 목적지를 설정해 실제 안내를 켜 둔다. 사용자 사진의 경로를 그대로 유지해도 된다. 로그에서 다음을 확인한다.

```text
TBT routeId=... entries=... serviceAreaHints=...
TBT[0] type=... code=... distanceMeters=... description=...
```

확인할 항목:

1. 화면의 용인휴게소·덕평휴게소가 description에 실제로 오는가?
2. 해당 항목의 type이 41인가? 졸음쉼터는 99인가?
3. 수신 목록의 순서가 실제 진행 순서인가?
4. distance가 현 위치부터의 누적 거리인가, 안내 항목 사이의 거리인가?
5. 전체 경로 목록인가, 제한된 개수의 다음 안내인가? 재조회 시 갱신되는가?
6. 경로 변경·목적지 삭제 이후 이전 항목이 남는가?

raw 로그에는 실제 주행 경로 정보가 들어갈 수 있으므로 공개 공유 전 범위를 확인한다.

## 2. 자동 연결 상태

Application은 `PleosTbtServiceAreaSource`와 `ReviewedServiceAreas`를 연결한다. 시연 단계에서는 **내비에 저장한 실제 시설 좌표를 가져와 사람이 노선·방향을 확인 등록하는 방식**을 사용한다. 외부 API 키·졸음쉼터 CSV·임의 좌표가 필요하지 않다.

TBT로 다음 휴게소를 고르고, 현재 경로에서 확인 등록한 내비 시설의 좌표·POI로 실제 requestTrip ETA를 조회한다. 시설명·시간을 제안해 명확한 동의를 받은 뒤 같은 시설을 addWaypoint로 추가하고, 원래 목적지·경유지·옵션·안내 상태를 확인한다.

좌표는 SDK `getBookmarkInfo()` → `onBookmarkInfo(List<BookmarkInfo>)`로 읽는다. 모델에는 실제 위도·경도·이름·POI ID·Sub ID·Provider가 있다. `NAVI_ROUTE` 권한을 사용하며, 신규 NaviHelper를 만들지 않는다. 이 API의 에뮬레이터 반환 동작은 새 시험으로 확인해야 한다.

### 최초 시설 확인 등록

1. 기존 안내 경로를 유지한 채 내비에서 **현재 진행 방향의 용인휴게소**를 찾아 시설 상세에서 즐겨찾기에 저장한다. 같은 이름의 반대 방향 시설과 구분한다.
2. 갱신한 앱에서 P·속도 0 상태로 **내비 조회 → 휴게소 시설 불러오기**를 누른다.
3. TBT 이름과 일치하는 저장 시설의 이름·주소·좌표를 확인해 선택한다. 후보가 1개여도 자동 확정하지 않는다. 노선·방향은 사람이 확인한다.
4. 확인한 노선명과 방향을 입력하고 체크한 뒤 **이 경로의 시설 확인 저장**을 누른다.
5. **이름·ETA 미리보기**로 실제 SDK 소요 시간과 제안 문장을 확인한다. 이 버튼은 경로 변경·녹음을 하지 않는다.

방향 확인 기록은 해당 routeId·목적지·경로 옵션·다음 휴게소 이름 순서에만 적용한다. 경로가 바뀌거나 첫 휴게소가 달라지거나 확인 후 24시간이 지나면 다시 확인한다. 확인 기록은 로컬 앱 설정에 저장하며 Room DB 스키마·기존 이력을 바꾸지 않는다. 전체 즐겨찾기 목록을 저장하거나 로그에 출력하지 않는다.

저장된 시설은 자동 후보 검색을 위한 전국 데이터베이스가 아니다. **방향 판단을 자동화했다고 설명하지 않는다.** 현재 단계의 방향 근거는 `MANUAL_ROUTE_DIRECTION_CONFIRMATION`이며 이력에도 이 방법을 기록한다. 미등록 시설·중복 확인·오래된 확인은 `SERVICE_AREA_DETAILS_UNAVAILABLE`로 종료한다.

### 기기 검증 순서

**현재 권장 경로는 앱 안에서 실행하는 시험이다.** 사용자가 `-WriteReviewedServiceArea`를 실행했을 때 저장 기록은 남아 있었지만 `reasons=ROUTE_ID:1`만 불일치했다. 설치·계측 재시작 사이의 ID 변경인지 실제 재탐색인지 아직 확정하지 않았다. 목적지·옵션·앞선 휴게소 이름이 같다는 사실만으로 기존 routeId 검사를 무시하거나 새 ID에 등록을 자동 이전하지 않는다.

1. 아래 기본 명령으로 앱을 갱신한다.
2. 앱 화면에서 현재 경로의 시설을 다시 확인 저장하고 **이름·ETA 미리보기**가 되는지 확인한다.
3. 앱을 재시작하지 않고 같은 화면의 **실제 추가·복원 시험**을 누른다. 끝날 때까지 P·속도 0을 유지한다. 내비가 앞으로 전환되어도 시험은 앱 범위의 작업과 전용 shortService에서 계속된다. 완료 후 앱의 내비 조회 탭으로 돌아와 결과를 확인한다.
4. 실제 경유지 추가·원래 목적지 보존·시험 경유지 삭제 결과를 확인한다. 음성 동의 시험은 아니다.

이 버튼은 기존 자동 개입을 잠시 정지하고, 현재 프로세스의 같은 NaviHelper/등록 컨텍스트로 제안·추가·삭제를 수행한 뒤 원래 자동 개입 활성 상태를 복구한다. 실제 추가 직전과 삭제 직전에도 정차 조건을 검사한다. 사용자 경로·옵션·경유지가 예상 상태와 다르면 자동 삭제하지 않고 정리 실패를 표시한다. 이 경우 내비 화면을 직접 확인한다.

화면 이탈 대응 구현 후 main/기기 시험 Kotlin 직접 컴파일과 JVM 테스트 118개를 통과했다. 회귀 시험은 ID 불일치 거부 유지, 최종 정차 조건 이탈 시 쓰기 차단, 취소 뒤 정리 완료 대기, 복원 불일치 표시, 자동 개입 활성 상태 복구와 중복 실행 방지에 더해 화면 관찰자 종료 후 작업 지속, 결과 재조회, 프로세스 중단 표시, 실행 제한 시간 뒤 정리 결과 보존을 검증한다. 실제 SDK 추가 화면은 사용자 제공 화면으로 확인했지만 자동 삭제·복원 완료와 이번 화면 이탈 대응의 기기 실측은 남아 있다.

Compose 화면 해제는 실제 시험을 취소하지 않는다. 명시적 작업 취소가 발생해도 이미 요청된 시험 경유지는 NonCancellable 정리 단계에서 확인한다. 실행 제한은 90초, 별도 정리는 최대 55초이며 전용 서비스는 150초에 종료한다. 마이크·녹음 없이 사용자가 시작한 시험 동안만 서비스를 유지하며 자동 재시작하지 않는다. 정리 중에는 새 시험을 시작하지 못하게 한다.

추가 결과와 삭제·복원 결과는 Application 소유 StateFlow와 별도 SharedPreferences에 보관한다. 앱 화면에 돌아오거나 프로세스를 새로 열어도 최근 결과를 확인할 수 있다. 처리 중 프로세스가 종료된 기록은 완료로 간주하지 않고 확인 필요로 표시하며 쓰기를 자동 재시도하지 않는다. 서비스 로그 태그는 `NaviWaypointProbe`, 구분자는 `NAV_PROBE_SERVICE`다. 실제 피로 판단/음성 동의 이력으로 저장하지 않는다.

```powershell
# 1. 갱신 빌드/설치 + TBT/휴게소 즐겨찾기 조회
.\scripts\Test-RestNavigation.ps1

# 2. 위 UI에서 시설 확인 저장 후, 실제 제안·ETA 조회만 검증
.\scripts\Test-RestNavigation.ps1 -PreviewProposal

# 3. 명시적 실제 추가 시험: 등록 시설을 추가·확인한 뒤 시험 경유지를 삭제
.\scripts\Test-RestNavigation.ps1 -WriteReviewedServiceArea
```

위 CLI 미리보기·쓰기 명령은 남겨 두었지만 설치/계측 시작 뒤 routeId가 달라지면 의도대로 거부한다. 등록 직후 실제 쓰기를 확인할 때는 위의 같은 앱 화면 버튼을 우선 사용한다.

기본 조회 로그의 `SERVICE_AREA_BOOKMARKS`와 `MATCHING_SERVICE_AREA`에서 반환 여부를 확인한다. 일치 항목이 없으면 내비의 즐겨찾기 이름이 휴게소명과 일치하는지 확인한다. 임의 근처 시설로 대체하지 않는다.

시설 목록이 비어 있을 때 화면에 **내비 즐겨찾기 수신 / 휴게소명 인식 / 대상 일치** 개수를 표시한다. 수신이 0이면 SDK가 빈 즐겨찾기를 반환한 것이며, 수신은 있지만 휴게소명 인식 또는 대상 일치가 0이면 저장 이름·시설명이 매칭되지 않은 경우다. 실제 기본 내비에 올바른 시설을 저장했는데 수신이 계속 0이면 Bookmark API의 저장 항목 범위를 추가로 실측해야 한다. 이때 임의 좌표나 다른 시설로 대신 등록하지 않는다.

사용자 화면에서 즐겨찾기 3개가 수신됐지만 `용인휴게소 강릉방면`이 휴게소로 인식되지 않는 버그를 확인해 수정했다. 기본 이름·괄호 방향·괄호 없는 `강릉방면`/`강릉방향`을 같은 시설 기본 이름으로 정규화한다. 원본 시설명·POI·좌표·방향 표시는 그대로 보존하고, 방향 확인과 선택은 여전히 명시적으로 받는다. 즐겨찾기 표시 이름을 변경할 필요는 없다.

두 번째 명령은 `REVIEWED_PROPOSAL`·`REVIEWED_PROMPT`만 출력하며 실제 경로를 바꾸지 않는다. 세 번째 명령은 **음성 동의 대신 사용자가 명시한 시험 명령으로 실제 경로를 변경**하는 SDK 통합 시험이다. `REVIEWED_WRITE status=VERIFIED_WAYPOINT`와 `REVIEWED_CLEANUP_CONFIRMED`를 확인한다. 실제 운전자 음성 동의·전체 DANGER 자동 발동 성공과는 구분한다.

### PreviewProposal에서 시설 확인 기록을 찾지 못할 때

빌드·설치가 성공해도 **내비 즐겨찾기 저장과 앱의 노선·방향 확인 저장은 별개**다. 위 UI에서 시설 선택·노선·방향 입력·체크·확인 저장을 마친 뒤 미리보기해야 한다. 이미 저장했더라도 목적지·경로·옵션·다음 휴게소 순서가 달라지면 재확인이 필요하다. 이 조건을 완화해 자동 추가하지 않는다.

미리보기 실패 시에도 스크립트는 현재 실행의 `REVIEWED_PREPARE_FAILED` 로그를 출력한다. 진단은 ASCII 코드로도 제공한다.

| 코드 | 의미 |
| --- | --- |
| REVIEW_NOT_REGISTERED | 앱에 시설 확인 저장 기록이 없음 |
| REVIEW_CONTEXT_MISMATCH | 기록은 있지만 현재 조건과 불일치 |
| REVIEW_DUPLICATE | 현재 조건과 일치하는 기록이 중복됨 |
| ROUTE_ID / ROUTE_OPTION / DESTINATION / UPCOMING_SEQUENCE | 불일치한 구체적 조건 |
| EXPIRED / CLOCK_REVERSED | 확인 만료 또는 기기 시계 변경 |

PowerShell 스크립트는 native ADB 출력 수신 중 UTF-8을 사용하고 종료 시 기존 인코딩을 복구한다. 앱 설치는 계속 `-r`이며 등록 기록이나 Room DB를 초기화하지 않는다.

진단 보강 후 main/기기 시험 Kotlin 직접 컴파일과 JVM 테스트 103개를 통과했다. 새 회귀 시험은 등록 없음·조건 불일치·중복 등록을 구분하는지 확인한다. 실제 저장 기록의 유무는 사용자 기기의 새 진단 로그로 확인해야 한다.

실제 자동 DANGER에서만 같은 제안·음성 동의·추가 흐름을 수행한다. CAUTION·수동 음성 5/6번·Replay는 경로를 변경하지 않는다. 제안 대상 시설이 지나갔거나 바뀌면 다음 시설로 몰래 바꾸지 않고 새 확인/제안을 요구한다.

다른 지도에서 새로 계산한 경로를 현재 Pleos 안내 경로와 같다고 취급하지 않는다. 실제 `requestTrip`의 탐색 거리·시간도 **해당 좌표까지의 별도 탐색 결과**다. 원래 경로상의 정확한 누적 거리·ETA를 얻었다고 설명하지 않는다.

## 3. 제안·동의·적용 계약

상세 정보가 준비된 공급자는 `RouteServiceAreaSource`를 구현한다. 이 계약은 단순 주변 장소 목록과 다르다.

| 필드 | 요구 사항 |
| --- | --- |
| routeId | 현재 실제 Navi 경로와 일치 |
| observedAtMs | 단조 시계 기준, 미래가 아니며 조회 시 30초 이내 |
| complete | 다음 휴게소를 판정하기에 충분한 목록이라는 근거가 있어야 true |
| onCurrentRoute / sameDirection | 현재 경로·진행 방향에서 접근 가능한 시설이라는 근거 |
| kind | SERVICE_AREA만 후보. SLEEP_REST_AREA·OTHER 제외 |
| routeOrder | TBT의 수신 순서. 등록 시설 경로에서는 이 순서로 선택 |
| distanceAlongRouteMeters | 실제 누적 경로 거리를 아는 공급자만 제공. TBT 등록 시설에서는 null |
| tripInfo | 실제 requestTrip의 별도 탐색 거리·시간. 모의 값 거부 |
| place | 실제 시설명·식별자·유효 좌표 |
| etaSeconds | 실제 공급자가 확인한 도착 소요 시간. 임의 속도 계산 금지 |

대상은 **TBT 수신 순서의 첫 휴게소**다. 실제 누적 경로 거리가 있는 별도 공급자에서는 그 거리순을 쓸 수 있다. 두 순서 기준을 섞지 않는다. 직선거리나 최단 ETA로 다른 시설을 고르지 않는다. 앞선 휴게소 정보가 잘못됐으면 뒤의 휴게소를 몰래 다음 휴게소로 제안하지 않는다.

`RestProposal`은 이름·ETA·시설·원래 목적지·경로 id·생성/만료 시각·출처를 고정한다. 질문 예:

> 휴식이 필요해 보여요. 현재 경로의 다음 휴게소는 ○○휴게소예요. 내비 예상 소요 시간은 약 8분이에요. 경유지로 추가할까요?

이 질문은 실제 정보가 준비됐을 때만 재생한다. `추가해 줘`, `안내해 줘`, `네` 등의 명확한 긍정만 허용하며 부정 표현이 우선한다. 거절·불명확·무응답·인식 실패에는 요청하지 않는다.

- 제안은 60초 이내·한 번만 적용할 수 있다. 변조·만료·폐기·이전 제안 재사용을 거부한다.
- 동의 후 다른 휴게소를 새로 선택하지 않는다.
- 동의 후 경로·목적지·경유지·옵션을 재조회한다. 같은 목적지라도 경로 id가 바뀌면 새 제안/동의가 필요하다.
- 휴게소를 이미 지나쳤는지 경로상 후보를 다시 확인한다. 제안한 곳이 더 이상 다음 휴게소가 아니면 새 제안/동의가 필요하다.
- SDK 최종 요청 직전에도 만료·조회 정보 유효 시간을 확인한다.

## 4. 기존 처리 보존

- 기존 SDK 조회·출발 전 판단은 Application의 동일 Repository를 사용한다.
- 원래 목적지가 없거나 기존 경유지가 있으면 자동 추가하지 않는다. 기존 경유지 삽입 동작은 별도 실측 후 확장한다.
- CAUTION·수동 음성 시험·Replay에는 휴게소 경로 쓰기를 붙이지 않는다. 수동 DANGER 음성 시험은 시험임을 명시한다.
- 경유지 요청은 `addWaypoint(FIRST)`를 사용한다. 목적지 재설정·안내 취소·옵션 변경으로 대체하지 않는다.
- 요청 후 목표 경유지·원래 목적지·옵션·실제 안내를 확인해야 `VERIFIED_WAYPOINT`다. 새 routing 완료 이벤트가 없으면 최소 500ms 간격의 두 연속 조회에서 이 조건과 같은 routeId를 확인해야 한다. 완료 이벤트만으로는 성공하지 않는다.
- 요청 후 취소는 이미 적용됐을 수 있음을 단일 이력에 남긴다. 사용자 경로를 임의로 원복하지 않는다.
- 제안 문장·동의·선택한 시설·출처·원래 경로·요청/확인 결과를 기존 actionDetails JSON에 저장한다. Room 스키마·기존 이력은 변경하지 않았다.
- 공조 정책 변경은 내비 작업 이후로 유지한다.

## 경유지 좌표 누락 대응

후속 사용자 화면은 `reasons=WAYPOINT_COORDINATES`, 안내 모드·경로 옵션 동일, 경유지 1개, `waypointDeltaMeters=13209994`였다. 등록 좌표에서 `(0,0)`까지 계산한 거리의 정수 부분이 이 값과 일치한다. 좌표 누락을 시사하지만 원시 콜백 좌표를 직접 수집한 결과와는 구분한다.

기존 매핑이 버리던 SDK `WaypointInfo`의 POI ID·sub ID·provider와 표시 좌표를 `NaviWaypoint`에 보존한다. 유효한 경유지 좌표는 기존 50m 검사를 유지한다. 경유지 좌표가 정확히 `(0,0)`일 때만 비어 있지 않은 실제 POI ID(`0` 제외)·sub ID·provider의 완전 일치를 검사한다. 유효한 표시 좌표가 있으면 추가로 50m 이내여야 하며, 표시 좌표도 없으면 전체 시설명까지 일치해야 한다. 잘못된 비영 좌표나 유효하지만 먼 좌표는 POI가 같아도 거부한다. 이름만 같은 시설이나 반대 방향 sub ID는 허용하지 않는다. 목적지·옵션·안내 모드·경유지 개수 보호는 유지한다.

후속 진단은 좌표 미제공을 13,000km 거리로 표시하지 않고 `positionAvailable=false`, `waypointDeltaMeters=NA`와 POI 필드별 일치 여부를 표시한다. 사용자 재실행 화면에서 `poiIdMatch=true`, `poiSubIdMatch=true`, `providerMatch=true`, `nameMatch=true`, `reasons=NONE`과 `삭제·복원=VERIFIED`를 확인했다. 추가 결과는 `routingCompleted=false` 때문에 `REQUEST_UNCONFIRMED`로 남았다.

이에 추가 완료 판정은 완료 이벤트와 일치하는 실제 상태 조회, 또는 완료 이벤트 없이 연속 두 번 일치하는 실제 상태 조회를 사용하도록 수정했다. 후자는 같은 routeId·원래 목적지·옵션·실제 안내·정확한 경유지가 유지되어야 하고 중간 불일치나 routeId 변경 시 연속 횟수를 초기화한다. 요청 전 경로 변경 거부와 삭제 전 사용자 변경 보호는 유지한다. 이 판정은 경유지 반영 확인이며 SDK의 라우팅 완료 이벤트 수신이나 정확한 경로 형상 계산 완료를 뜻하지 않는다. 로그의 `ADD_VERIFIED evidence=STABLE_READBACK`으로 구분한다. 이벤트 미수신 대응의 기기 재실측은 남아 있다.

## 5. 검증과 한계

**최신 기기 검증: 성공.** 2026-11-12 사용자가 제공한 화면에서 실행 코드·결과 코드가 모두 `STABLE_POI_V2`, 시험 번호 `4cb9f218`, 추가 `VERIFIED_WAYPOINT`, 삭제·복원 `VERIFIED`임을 확인했다. 화면에는 실제 경유지 추가·원래 목적지 보존·시험 경유지 삭제 확인 메시지가 남았다. 진단용 설치 패키지는 `ai.pleos.playground.sample.vehicle.diagnostic`, Activity 클래스는 `ai.pleos.playground.sample.vehicle.MainActivity`이므로 실행 컴포넌트는 `ai.pleos.playground.sample.vehicle.diagnostic/ai.pleos.playground.sample.vehicle.MainActivity`다. 앞선 명령의 기존 패키지 지정 오류를 정정한 뒤 성공 화면을 받았다. 이전 실패 전부가 패키지 혼동 때문이었다고 단정하지 않는다. 아래의 미확인·재실측 필요 기록은 이 성공 확인 전의 경과다.

이 결과는 사용자가 시설·노선·방향을 확인 등록한 정차 에뮬레이터에서 음성 없이 수행한 추가·삭제 왕복 시험의 성공이다. 음성 동의부터의 DANGER 통합 동작, 주행 중 동작, 미등록 시설 자동 식별, 정확히 동일한 원래 경로 형상 복원을 검증한 것은 아니다. 실제 서비스용 경유지는 이 시험 버튼과 달리 자동 삭제하면 안 된다.

연속 조회 판정 수정 뒤에도 사용자는 `REQUEST_UNCONFIRMED / VERIFIED`, `routingCompleted=false reasons=NONE`인 결과 화면을 제공했다. 이 화면에는 당시 실행 코드와 결과 기록 버전이 없어 최신 코드 실행·과거 결과 재표시·연속 조회 중 routeId 변동 등을 구분할 수 없다. 이전 버전 결과로 단정하지 않는다. 이를 위해 실행 코드와 저장 결과의 `verifierRevision=STABLE_POI_V2`, 시험 runId 앞 8자리를 화면에 표시하고, 실제 판정의 reads·matches·mismatches·routeChanges·decision을 추가 확인 실패 메시지와 `ADD_READBACK` 로그에 기록한다. 과거 저장 결과는 버전을 추정하지 않고 `이전 버전·미기록`으로 표시한다. 추가한 진단 버전의 main/기기 시험 Kotlin 직접 컴파일 및 JVM 테스트 126개를 통과했으며 기기 문제 해결은 아직 확인되지 않았다.

main Kotlin·신규 기기 시험 Kotlin은 기존 캐시의 SDK·Compose compiler로 직접 컴파일한다. 개입/음성/내비 JVM 테스트는 합성 입력으로 선택 순서·필터·동의·토큰·취소·TBT 유형 분리를 검증한다.

이번 등록 기능 반영 후 main Kotlin 직접 컴파일·개입/음성/내비 JVM 테스트 100개·기기 시험 Kotlin 직접 컴파일을 통과했다. 신규 시험은 미확인 시설 거부, 반대 방향 동명 후보의 명시 선택, 경로·목적지·옵션·휴게소 순서 변경, 등록 만료, 정차 이탈, 모의 ETA 거부와 등록된 정확한 POI의 제안→음성 동의→적용 연결을 다룬다. 합성 포트/음성으로 검증한 결과이며 실제 SDK 동작 성공을 대신하지 않는다.

사용자 실행으로 정식 Gradle 빌드·갱신 설치·실제 TBT 및 즐겨찾기 조회·시설 확인 등록·이름/ETA 미리보기·휴게소 경유지 추가와 목적지 보존 화면을 확인했다. 화면 이탈 후 결과 보존 및 자동 삭제·원래 안내 상태 복원도 사용자 결과 화면으로 확인했다. 완료 이벤트 미수신 대응은 추가 기기 실측이 필요하다. 에이전트 실행 환경의 Gradle 내부 연결·ADB 제약과 실제 에뮬레이터가 동작한다는 사실을 구분하며, 직접 Kotlin 컴파일·JVM 회귀 시험을 실제 SDK 통합 성공으로 대신하지 않는다.

기존 명시적 쓰기 프로브는 남겨 두었다. 사람이 검증한 좌표로만 `-WriteWaypoint -Latitude ... -Longitude ...`를 지정한다. 이 시험은 SDK 추가/삭제 프로토콜 시험이며, 그 좌표가 실제 경로상 다음 휴게소임을 검증하는 시험은 아니다.
