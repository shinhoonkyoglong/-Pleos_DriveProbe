# 주행 테스트 도구 E2E 결과

검증일: 2026-11-13 (Asia/Seoul). 브랜치: `codex/driving-test-runner`.

후속 [실제 경유지 추가 검증](waypoint-verification.md)을 수행했다. 항목 생성·목적지 보존은 확인했지만, SDK가 경유지 좌표와 POI ID를 비워 반환해 `REQUEST_UNCONFIRMED`로 완료 판정은 실패했다. 시험 경유지 제거 후 목적지 유지·경유지 0개도 재조회했다.

## 실행 환경과 범위

- 실제 Pleos 에뮬레이터 `emulator-5554`, AAOS 사용자 10, 설치된 프로젝트 Debug 앱.
- Virtual Console REST → 실제 차량 신호 저장소 → REAL 피로 엔진 → 생산 개입 처리 → Room 주행·개입 저장 → 요약 로그까지 실행했다.
- 앱 Kotlin 코드는 변경하지 않았다. Debug APK가 제공하던 실제 SDK 경로를 사용했다.
- 9분 전체 주행과 3분 음성 재시험을 수행했다. 별도로 15초 Smoke도 통과했다.

| 항목 | 결과 | 근거 |

| 정상 주행 3분 | 통과 | 유효 창 생성 후 NORMAL 유지 |
| 졸린 조향 입력 | 통과 | MILD → CAUTION으로 상승 |

| CAUTION 무응답 | 통과 | 첫 실행에서 실제 질문·대기 후 `NO_RESPONSE`, 해당 주행 이력 저장 |
| CAUTION 음성 응답 | 통과 | 두 번째 실행에서 “괜찮아요” 인식, `ANSWERED`, 같은 주행 ID로 저장 |
| DANGER 시설 미확인 처리 | 통과 | `UNAVAILABLE / SERVICE_AREA_DETAILS_UNAVAILABLE`. 현재 경로와 맞지 않는 시설 확인으로 경유지 추가를 진행하지 않음 |
| DANGER 동의 후 경유지 추가 성공 | 미검증 | 현재 경로의 시설 확인을 준비하지 못했다. 위 실패 처리 통과를 추가 성공으로 간주하지 않음 |
| P 정차·주행 저장·요약 로그 | 통과 | 두 실행 모두 P·속도 0·조향 0 재조회, 동일 주행 ID의 Room 기록과 요약 로그 확인 |
| 주행·요약 화면 자동 전환 | 미검증 | 실행 중 내비 앱이 전면에 있었다. 로그·DB 성공을 화면 표시 성공으로 간주하지 않음 |

음성 성공 시험에는 PC의 실제 마이크를 사용하지 않았다. Windows의 설치된 한국어 음성으로 만든 16kHz 모노 PCM WAV를 로컬 에뮬레이터의 공식 `EmulatorController.injectAudio`로 넣었다. 앱의 Pleos TTS·AudioRecord·Pleos STT·판정·Room 저장은 실제 경로다. 합성 입력 시험이며 사람의 응답 시간 정확도를 검증한 결과는 아니다.

합성 입력 도우미의 스트림 종료에서는 `DEADLINE_EXCEEDED`가 한 번 발생했다. 그 전에 앱에서 `PCM STT final chars=4`와 `ANSWERED` 저장을 확인했고, 재시험의 필수 개입 판정 및 별도 Room 검사는 통과했다. 스트림 종료 반환값을 음성 인식 성공의 근거로 사용하지 않았다.

컴퓨터 화면 제어는 사용자의 Esc 입력으로 중단됐다. 이후 Windows 마우스·키보드 조작을 하지 않고, 이미 승인된 에뮬레이터 SDK 입력과 로그·DB 검사로 검증을 이어갔다.

## 실행별 증거

결과 폴더는 `artifacts/driving-tests/` 아래에 있으며 Git에서 제외된다. DB 검사는 기기의 DB를 수정하지 않고 PC 임시 SQLite 복사본에서 이번 주행만 추출했다.

| 실행 | 명령·구성 | 결과 |
| --- | --- | --- |
| `20261113-112040-4ca713` | `-Scenario Danger`: 정상 3분 → 졸림 3분 → 심한 졸림 3분 | 자동 판정 10항목 PASS, DB 검사 PASS. 실제 저장 시간 541,565ms, 최고 DANGER, 판정 시간 481,046ms |
| `20261113-113030-663d04` | `-Scenario Fatigue -NormalMinutes 0 -RequireInterventions` | 자동 판정 12항목 PASS, DB 검사 PASS. 실제 저장 시간 181,549ms, 최고 CAUTION, MILD VERIFIED·CAUTION ANSWERED |

첫 실행의 개입 이력은 85·86·87, 두 번째는 88·89다. 실제 이력의 `simulation=false`와 주행 ID 연결을 확인했다. 현재 코드의 휴식 권고 집계는 DANGER만 세므로 첫 실행은 권고 1·응답 0, 두 번째는 권고 0·응답 0으로 저장됐다. CAUTION 응답은 원본 개입 이력에서 확인했다.

각 폴더의 `result.md`, `result.json`, `app.log`, `database-check.json`이 근거다. 첫 실행에는 정상·CAUTION·종료 시 Android 화면 PNG도 보존했다. 내비 전면 상태를 보여 주는 자료이며 계속운전 주행 화면의 표시 증거는 아니다.

## E2E 중 수정한 도구 문제

초기 시도에서 REAL 전환은 일어났지만 logcat 부착 중 첫 엔진 시작 로그를 놓쳤다. 수집기에 고유 표식이 들어온 것을 확인한 뒤 REAL 모드로 바꾸도록 수정했다. 판정에는 표식 이후의 해당 앱 PID 로그만 사용한다. 장치 로그 버퍼는 지우지 않는다.

원본 로그 파일을 쓰는 중 읽을 때는 `FileShare.ReadWrite`를 사용하도록 수정했고, 이후 9분·3분 실행 모두 수집과 결과 생성에 성공했다.

도구 회귀 검사는 Windows PowerShell 5.1·PowerShell 7에서 판정 검사 28개, 가짜 REST 서버와 실행 도구 검사 10개를 통과했다. HTTP·정차 요청 실패, 이전 로그·다른 앱 PID 혼입, ADB 명령 제한 시간과 연결 확인을 포함한다.

## 정리와 남은 촬영 준비

> 후속: 에뮬레이터 복구와 실제 경유 항목 생성은 [경유지 검증](waypoint-verification.md), 주기적 재탐색·빈 SDK 좌표 처리 수정은 [DANGER E2E 수정](rest-stop-e2e-fix.md)을 참고한다. 아래 내용은 최초 주행 시험 당시 기록이다.

- 차량은 P·속도 0·조향 0으로 정리했다.
- 테스트에서 변경한 공조는 시작 전 값인 운전석 22℃·풍량 3·AUTO OFF·전원 OFF로 복원했다.
- 합성 입력 도우미를 종료하고 에뮬레이터 호스트 마이크 연결을 다시 켰다. 테스트용 음성 준비 해제를 위한 앱 종료 명령을 실행했다.
- 앱 종료 후 마지막 상태 재조회 중 ADB·Virtual Console REST·에뮬레이터 gRPC가 모두 응답하지 않았다. 따라서 음성 서비스의 최종 종료 상태는 재확인하지 못했다. 공조 복원과 P·속도 0·조향 0은 그 전에 확인했다. 대기 중이던 이번 작업의 ADB 조회 클라이언트는 정리했다.
- 이 상황을 반영해 실행 도구의 단일 ADB 명령에 기본 15초 제한 시간을 추가했다. 응답하지 않는 가짜 ADB 프로세스로 무한 대기 방지를 검사한다.
- 이번 주행·개입 DB 기록은 증거로 보존했다. 실제 주행 기록으로 저장되므로 이후 화면 집계에도 나타날 수 있다.
- 촬영 전에는 현재 경로의 휴게시설 확인을 다시 준비해 DANGER 동의 후 경유지 적용을 확인하고, 계속운전 앱을 전면에 둔 상태의 화면 흐름을 별도로 확인해야 한다.
